Design guidance

  • The common default is density + jittered points + box plot. In Correll's survey of 50 published rainclouds: density in 48, jitter in 40, box plot in 38.
  • Random jitter "hallucinates": identical data looks different every render, and the jitter axis means nothing. Prefer deterministic rain (strip, beeswarm, dot plot). Try Group C above: jitter hides that it is whole numbers; barcode and dot plot show it.
  • Bandwidth is the main trap. The default smooths over gaps; drag the slider down and Group B's gap appears. Scherer tunes it; the Power BI violin exposes it as a setting, with per-category values.
  • Don't draw density beyond the data. The engine here clips each cloud to the group's observed range.
  • Label the lightning. Whiskers, IQR and 90% intervals look alike; say which one is drawn.
  • Split, not mirrored: Correll prefers a half density to a violin, since the mirror adds no information.
  • A beeswarm can be enough: if it shows the density legibly, the cloud may be redundant. That needs a toggle, not a fixed design.

Recommendation

There is no JS raincloud worth porting as-is. The D3 examples are toy demos with no licence, and the good implementations are R and Python. So we port the design (ggrain's feature set, ggdist's look, Correll's defaults) and write the engine in D3 ourselves. It is small: the engine drawing this page is about 300 lines, with a Gaussian KDE, Silverman bandwidth, quantiles, a deterministic beeswarm and a dot plot.

Suggested defaults for the extension: half density clipped to the data, slim box with labelled whiskers, beeswarm rain, bandwidth control, percentile truncation with overflow counts. Repeated-measures lines (ggrain) are a strong later feature.
